A shopping assistant searching a product catalog has to issue multi-step tool calls, inspect candidate items, and recommend products that satisfy every constraint in the shopper's request. Large frontier models navigate this search-and-verify loop reliably, but serving them across high-volume catalog traffic is costly. Compact 4-billion-parameter models fit comfortably on a single commodity GPU, yet out of the box they often terminate early or skip the catalog lookups needed to ground a recommendation.

Training a small model on every raw transcript from a larger teacher model introduces its own problem: even strong teachers fail on a fraction of multi-constraint queries. If the student imitates unverified rollouts, or spends capacity fitting user prompt tokens rather than agent decisions, small-budget fine-tuning can reinforce flawed tool habits.

In this post, we build a bounded sequence-distillation pipeline for `Qwen/Qwen3.5-4B` on the ShoppingBench product task. We filter teacher trajectories with the benchmark's deterministic scorer, train a 4-bit QLoRA adapter with assistant-only loss masking, and compare the base model against the distilled student inside the same live ReAct catalog loop.

## Solution overview

The pipeline separates offline trajectory curation from online agent evaluation. During preparation and training, the harness scores candidate teacher trajectories against the catalog ground truth, keeps only solved rollouts, encodes them with prompt tokens masked out, and updates a 4-bit QLoRA adapter on `Qwen/Qwen3.5-4B`.

During evaluation, both the unmodified base model and the adapted student run against a held-out product query through the same local OpenAI-compatible loopback server and the native ShoppingBench ReAct loop. Toggling the LoRA adapter on a single loaded quantized model isolates the behavioral effect of the distillation updates.

Three gates keep the experiment honest. First, training and held-out queries are checked for zero overlap before any rollout is read. Second, the native scorer filters teacher traces before supervised encoding so failed trajectories never enter the optimizer. Third, evaluation runs the actual multi-step catalog search tools and deterministic scorer rather than checking static token perplexity.

## Filter teacher trajectories with the benchmark scorer

Sequence-level knowledge distillation starts with trajectories generated by a stronger teacher agent—here, published `GLM-5.3` product rollouts from the [pinned sequence-distillation recipe](https://github.com/aws/sagemaker-hyperpod-recipes/tree/520b248f47f488f60af52f40ee6172f606894e59/examples/sequence-distillation). Rather than trusting every teacher transcript, the preparation stage runs the benchmark's native scorer (`score_rollouts.py`) against the local catalog index first.

The following excerpt comes from `prepare(run)` in [`workflow.py`](https://github.com/recohut/agent-kit/blob/2c695d8e030c58b76f66e42c96fb33c74ba4e086/examples/shopping-agent-sequence-distillation/workflow.py).

```python
training, held_out = load_split(SB / "data", "product")
if {row["query"] for row in training} & {row["query"] for row in held_out}:
    raise RuntimeError("The training and held-out split overlaps.")
problems = run / "train-product.jsonl"
write_jsonl(training, problems)
rollout = run / "teacher-product.jsonl"
with gzip.open(ROOT / TRACE, "rb") as source, rollout.open("wb") as dest:
    dest.writelines(islice(source, 12))
scores = run / "teacher-scores.json"
result = subprocess.run(
    [str(PYTHON), str(ROOT / "scripts/score_rollouts.py"), "--task", "product",
     "--rollouts", str(rollout), "--problems", str(problems), "--per-query", str(scores)],
    cwd=SB, env=_env(), capture_output=True, text=True, timeout=900,
)
solved = {q for q, score in json.loads(scores.read_text()).items() if score["solved"]}
return sft_rows(rollout, solved, include_reasoning=True), held_out[0], len(solved)
```

The split check verifies that no held-out evaluation query appears in the training pool. Next, the harness scores the first 12 teacher product trajectories against the problem definitions and writes per-query outcomes to `teacher-scores.json`.

In the recorded run, **8 of the 12 teacher trajectories** passed the scorer (`{'solved_teacher_tasks': 8}`). Only those 8 solved queries pass into `sft_rows(..., include_reasoning=True)`, which extracts the reasoning and tool-call turns for supervised fine-tuning. The 4 unverified teacher rollouts are discarded before training begins.

## Train on assistant turns within a bounded context

Multi-step agent transcripts pack tool schemas, catalog observations, and reasoning blocks into long sequences. To fit fine-tuning comfortably on a single 16 GiB T4 GPU, the training stage loads `Qwen/Qwen3.5-4B` in 4-bit NormalFloat (`nf4`) quantization with `float16` compute, enables non-reentrant gradient checkpointing, and selects four distinct solved queries that fit within a 2,048-token cap.

Crucially, the supervision labels mask every prompt token with `-100` so cross-entropy loss is computed exclusively over the assistant's thinking and tool-action tokens. The excerpt below is from `train(run, examples, solved_count)` in [`workflow.py`](https://github.com/recohut/agent-kit/blob/2c695d8e030c58b76f66e42c96fb33c74ba4e086/examples/shopping-agent-sequence-distillation/workflow.py).

```python
student = get_peft_model(
    student, LoraConfig(r=4, lora_alpha=8, target_modules=["q_proj", "v_proj"],
                        task_type="CAUSAL_LM"),
)
student.train()
optimizer = torch.optim.AdamW(
    (parameter for parameter in student.parameters() if parameter.requires_grad), lr=1e-4,
)
losses = []
for prompt, target in rows.values():
    ids = torch.tensor([prompt + target], device="cuda")
    labels = torch.tensor([[-100] * len(prompt) + target], device="cuda")
    optimizer.zero_grad(set_to_none=True)
    loss = student(input_ids=ids, labels=labels).loss
    if not torch.isfinite(loss).item():
        raise RuntimeError("Non-finite training loss.")
    loss.backward()
    optimizer.step()
    losses.append(loss.item())
```

Each update processes one complete solved trajectory (`prompt + target`) with rank-4 LoRA adapters attached to `q_proj` and `v_proj`. When the chat template already ends with an opening `<think>` tag, the encoder strips any duplicate leading `<think>` prefix from the target before tokenization so the assistant turn aligns cleanly with inference time.

In the recorded run across four distinct solved product tasks, the step losses were `0.8264`, `0.8013`, `0.8838`, and `0.9406`. Peak PyTorch allocated GPU memory reached **9.30 GiB**, leaving headroom on a single T4 GPU. After saving the adapter to `scored-adapter`, the workflow frees the training state and clears the CUDA cache before starting the benchmark harness.

## Evaluate base and student in the same ReAct tool loop

A lower training loss does not prove an agent can use tools to solve a new catalog query. To test actual task completion, `evaluate(run, case, adapter)` starts the local ShoppingBench catalog search service, launches a lightweight loopback `/v1/chat/completions` server in-process, and runs the native `react_loop` on a held-out product problem.

Both evaluation arms share the exact same quantized base weights in memory. For the `base` arm, inference runs inside `model.disable_adapter()`; for the `student` arm, inference runs with the trained QLoRA adapter active. This excerpt from the evaluation loop in [`workflow.py`](https://github.com/recohut/agent-kit/blob/2c695d8e030c58b76f66e42c96fb33c74ba4e086/examples/shopping-agent-sequence-distillation/workflow.py) shows the loopback completion handler and arm execution.

```python
with torch.inference_mode(), (model.disable_adapter() if mode == "base" else nullcontext()):
    output = model.generate(**encoded, max_new_tokens=512, do_sample=False)
content = tokenizer.decode(output[0, length:], skip_special_tokens=True)
```

The runner caps the agent at `MAX_STEPS = 8` and `512` generated tokens per step with greedy decoding (`do_sample=False`), and removes `web_search` so both models rely strictly on the local catalog search tools. After each arm finishes its rollout, the native scorer grades the resulting recommendation.

| Evaluation arm | Tool loop steps | Recommendation score | Task success (`asr`) | Elapsed time (s) |
| --- | --- | --- | --- | --- |
| Base `Qwen3.5-4B` (`disable_adapter()`) | 2 | 0.0 | **0.0 (Failed)** | 174.27 |
| Distilled `Qwen3.5-4B` (QLoRA adapter) | 4 | 1.0 | **1.0 (Passed)** | 259.45 |

On the held-out product task, the unmodified base model stopped after **2 steps** without locating a qualifying recommendation (`recommend: 0.0`, `asr: 0.0`). With the four-update sequence-distillation adapter enabled, the student executed **4 tool-loop steps**, refined its catalog query, and returned a qualifying product recommendation (`recommend: 1.0`, `asr: 1.0`).

## Limits and next steps

These recorded results establish an end-to-end mechanics proof on a single GPU: scoring 12 teacher trajectories, training 4 QLoRA updates within 9.30 GiB of VRAM, and comparing base versus student on 1 held-out product task. A single held-out task demonstrates that the pipeline transfers multi-step tool behavior end to end, but it does not measure broad accuracy across the full benchmark distribution.

The upstream recipe also defines `shop` and `voucher` task splits alongside larger teacher rollout pools. Scaling this workflow to production candidate selection requires training across the full set of scorer-approved trajectories, evaluating the complete held-out split across all three task families, and tracking latency and step-count distributions under concurrent serving.

When adapting this pattern to your own internal tools, keep the scorer gate ahead of SFT encoding. Even high-capability teacher models produce trajectories that violate tool schemas or miss business rules; filtering with a deterministic domain verifier prevents the student adapter from memorizing failed multi-step searches.
